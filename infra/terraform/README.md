# Terraform: PROD on AWS

The AWS side of `docs/PROD_ENVIRONMENT_PLAN.md`, in `af-south-1`.

| Folder | Creates |
|---|---|
| `bootstrap/` | The S3 bucket every Terraform state lives in. Run once |
| `prod/` | The PROD environment: VPC, EC2, Elastic IP, RDS, S3, ECR, SES SMTP user, IAM, CloudWatch alarms, the data-out budget |
| `prod-grafana/` | PROD's alert rules and their email contact point in the Grafana Cloud stack (#340) |

Versions are pinned: Terraform `1.16.6`, the AWS provider `6.69.1` and the Grafana provider
`4.50.0`, with `.terraform.lock.hcl` committed for Linux, macOS and Windows.

## Running Terraform

No local install is needed. From this folder, with AWS credentials from `aws login`:

```bash
eval "$(aws configure export-credentials --format env)"
tf() {
  docker run --rm -it -v "$(pwd -W 2>/dev/null || pwd):/tf" -w "/tf/$1" \
    -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN \
    hashicorp/terraform:1.16.6 "${@:2}"
}
tf prod init
tf prod plan
```

On Git Bash for Windows, prefix the `docker run` with `MSYS_NO_PATHCONV=1`.

## First run

1. **State bucket.** The bootstrap state cannot start in a bucket that does not exist yet, so it
   starts on disk and then moves into the bucket it created:

   ```bash
   tf bootstrap init -backend=false
   tf bootstrap apply
   tf bootstrap init -migrate-state      # answer yes; the local state file can then be deleted
   ```

2. **Alarm email.** Create `prod/terraform.tfvars` (git-ignored) with one line:

   ```hcl
   alarm_email = "you@example.com"
   ```

3. **PROD.** `tf prod init`, then `tf prod plan`, then `tf prod apply`. The plan should end with
   `1 to import, 62 to add, 1 to change, 0 to destroy`. The import is the SES identity created by
   hand in #330, and the one change adds the project tags to it.

4. **Confirm the alarm subscription.** AWS emails a confirmation link to `alarm_email`. No alarm
   is delivered until it is clicked.

## Grafana Cloud alerts

`prod-grafana/` has its own state (`prod-grafana/terraform.tfstate` in the same bucket), so a
`prod/` plan never asks for the Grafana token. It still needs the AWS credentials above, for the
state bucket.

1. **Token.** In the stack (`https://friendlysamosa508.grafana.net`): Administration > Users and
   access > Service accounts > Add service account, role **Editor**, then Add service account
   token. Copy it once; Grafana does not show it again.

2. **Alert email.** Create `prod-grafana/terraform.tfvars` (git-ignored) with one line:

   ```hcl
   alert_email = "you@example.com"
   ```

3. **Plan and apply,** with the token read from a prompt so it never reaches the screen, a file or
   the shell history:

   ```bash
   read -rsp "Paste Grafana token: " TF_VAR_grafana_auth && echo && export TF_VAR_grafana_auth
   tfg() {
     MSYS_NO_PATHCONV=1 docker run --rm -it -v "$(pwd -W 2>/dev/null || pwd):/tf" -w /tf/prod-grafana \
       -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN -e TF_VAR_grafana_auth \
       hashicorp/terraform:1.16.6 "$@"
   }
   tfg init
   tfg plan     # first run: 4 to add, 0 to change, 0 to destroy
   tfg apply
   unset TF_VAR_grafana_auth
   ```

   The first plan adds the `PROD alerts` folder, the `PROD alert email` contact point and two
   rule groups, `server` and `backend`. If it stops at `grafanacloud-friendlysamosa508-prom` not
   found, set `prometheus_data_source` in `terraform.tfvars` to the stack's Prometheus data source
   name (Connections > Data sources).

4. **Test it.** Alerting > Contact points > `PROD alert email` > Test. The mail should arrive within
   a minute. Then check Alerting > Alert rules: every rule should be `Normal`. A rule in `No data`
   means its series is not reaching the stack.

## What is protected

- `disable_api_termination` on the server, `deletion_protection` on RDS, and `prevent_destroy` on
  the S3 buckets and the SES identity. A `destroy` stops with an error until a person removes the
  protection on purpose.
- The RDS master password is generated by RDS and kept in Secrets Manager, never in state.
- The SES SMTP password is in state and in SSM Parameter Store (`/sas-prod/MAIL_PASSWORD`). That is
  why state lives only in the encrypted, private, versioned state bucket.

## What this does not do

- **DNS.** The `accommodation` A record and the move of `beezhub.co.za` to Route 53 are #344.
  Until then the record is added by hand at the current DNS host, pointing at the `public_ip`
  output.
- **The application.** The server comes up with Docker, Caddy, the AWS CLI and `psql` installed
  and `/opt/sas` empty. The first deploy is #336.
